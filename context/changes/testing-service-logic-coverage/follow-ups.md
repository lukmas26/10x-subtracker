# Follow-ups — testing-service-logic-coverage

Decided out of scope in `research.md` → Decisions (2026-10-22, user); recorded 2026-10-24. Each one is a **separate change**.

- **Crafted `?saved=1` / `?updated=1` shows a confirmation without a row (risk #4).** `/subscriptions` renders "Subscription saved" / "Subscription updated" whenever the query parameter is present (`src/pages/subscriptions.astro:12-13,41-55`). Unlike `?error=`, which goes through the `displayableError` allowlist (`src/lib/services/subscriptions.ts:52-59`), these flags are never checked, and no row is re-read. The server side is honest: the routes redirect with the flag only after a no-error RPC result (`src/pages/api/subscriptions.ts:29`, `src/pages/api/subscriptions/[id].ts:42`), now pinned by `tests/integration/subscriptions.routes.test.ts`. The fix is a code change in the page (for example, a one-time flash value or a re-read of the saved row), not just a test. Evidence: `research.md` §2, Decision 2.
- **A lost response after commit leads to a duplicate on retry: add an idempotency key (risks #2, #4).** If the connection drops after `create_subscription` commits, the user sees the save error although the row exists. Retrying the add creates a second subscription, because create has no client-supplied key (`supabase/migrations/20261003140000_create_subscription_rpc.sql:58-60`). postgrest-js does not resend a failed POST itself (`node_modules/@supabase/postgrest-js/dist/index.mjs:81-84`), so the duplicate comes from the user's retry. Local tests cannot simulate a response lost after commit without a proxy, so Phase 2 covers only failures before the request reaches PostgREST. Remedy: an idempotency key sent with the form and enforced by a unique constraint in the RPC; it can share a change with the entry above. Evidence: `research.md` §1 ("Dropped connection"), Decision 4.
